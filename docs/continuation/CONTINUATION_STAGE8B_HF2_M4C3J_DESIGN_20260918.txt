CURRENT SEPARATION — IMPORTANT
1. Native-selected clarify/ask:
   - native speech-act selection is already complete;
   - independent initiative/expression selection must choose express;
   - _prepare_resolution_transport creates one process-local dispatch;
   - POST /room/message returns _ResolutionRoomResponse;
   - only after the trusted terminal JSON response body send succeeds can complete_resolution_dispatch create ResolutionExecutionReceipt;
   - only that receipt can mark the speech-act/expression pending outcome;
   - later learning remains distinct and at most once.

2. Ordinary native expression:
   - room_message calls present_native_utterance(out.native_text, source='interaction')
     only when out._resolution_dispatch is None;
   - present_native_utterance independently invokes the existing native voice selector;
   - only a genuine native voice choice of voice creates/publishes a WAV artifact;
   - decoder/English remains downstream and observational;
   - NativePresentationRecord is presentation provenance, not speech-act execution.

3. Explicit exclusion:
Current api.py deliberately prevents native presentation for a resolution dispatch:
presentation is created only if out._resolution_dispatch is None.
Therefore native-selected clarify/ask has trusted text execution but no native audio presentation.

4. M4C3I:
Authenticated /room/files/{artifact_id} can now create NativeAudioTransportReceipt only after server-side audio ASGI send completion.
This receipt remains transport/provenance only and never means playback/hearing or speech-act execution.

ROOM CLIENT OBSERVATION
The private Room renders NativePresentationRecord audio with:
- an ordinary HTML audio element;
- controls enabled;
- no autoplay.

However, assigning audio.src may permit browser metadata/range fetching even without playback.
Therefore:
- NativeAudioTransportReceipt may exist without play();
- it must remain transport-only;
- browser fetch must never be used as the clarify/ask execution boundary.

DESIGN CONCLUSION
The safest M4C3J bridge is POST-EXECUTION presentation:

A. Keep the existing ResolutionExecutionReceipt as the one and only execution receipt for native-selected clarify/ask.
B. Do NOT create/publish a resolution audio presentation merely because content was prepared.
C. Do NOT create/publish it merely because the native expression selector chose express.
D. Only after complete_resolution_dispatch has durably recorded a valid ResolutionExecutionReceipt may the exact same native utterance be offered to the independent native voice selector.
E. If native voice selection remains unresolved or selects text-only, the already-valid speech-act execution remains valid and no audio presentation is created.
F. If a native voice presentation is created, it is downstream presentation of an already-executed act and must not mark speech-act or expression consequence pending a second time.
G. Later audio HTTP fetch creates only NativeAudioTransportReceipt and must not train speech-act consequence geometry.
H. Decoder English remains observational and downstream.

REQUIRED PROVENANCE
A resolution-derived NativePresentationRecord should carry explicit zero-authority linkage to the already-durable ResolutionExecutionReceipt, rather than relying on temporal proximity alone.

Recommended optional provenance fields:
source_resolution_receipt_id: UUID | None
source_resolution_event_id: UUID | None
source_resolution_action: clarify | ask | None
source_resolution_execution_confirmed: bool = false

For ordinary presentations these remain empty/false.
For resolution-derived presentations they are populated only after a valid durable ResolutionExecutionReceipt and after verifying:
sha256(exact native utterance) == receipt.native_text_sha256.

These fields are audit/provenance only.
They grant zero:
speech-act choice authority
execution authority
semantic truth
answer authority
preference
relationship meaning
cognitive-memory authority
source-write authority
deployment authority
peer delivery/hearing/understanding authority

RECOMMENDED IMPLEMENTATION BOUNDARY
1. Extend NativePresentationRecord only with optional resolution-execution provenance.
2. Extend present_native_utterance with optional already-executed resolution provenance parameters.
3. Extend complete_resolution_dispatch return data only enough to expose zero-authority receipt identity/event/action/native-text hash to the same trusted in-process adapter.
4. _ResolutionRoomResponse should retain the process-local exact native text privately.
5. After terminal JSON send completion:
   a. complete_resolution_dispatch first;
   b. require receipt_recorded=true;
   c. verify native-text SHA against returned receipt provenance;
   d. only then call present_native_utterance(... source='resolution-interaction', receipt provenance ...).
6. Presentation failure/unresolved native voice must NOT roll back or invalidate the already-durable ResolutionExecutionReceipt.
7. No presentation is created on:
   - response send failure;
   - stale/mismatched dispatch;
   - receipt persistence failure;
   - missing/changed native text hash.
8. Do not make audio presentation a prerequisite for clarify/ask execution.
9. Do not create a second speech-act pending marker for audio.
10. Do not change M4C3I NativeAudioTransportReceipt semantics.

CLIENT/API SURFACE
The JSON response body is serialized before the post-send resolution receipt exists.
Therefore the response body must not falsely claim that a resolution audio presentation already exists.

Safe choices:
- preserve presentation_id=None in that immediate response;
- optionally expose a zero-authority field such as native_presentation_deferred_until_execution_receipt=true;
- authoritative presentation state remains /room/state after the post-send commit.

A client may race and snapshot before post-send presentation commit is visible.
That is a UI freshness issue, not a cognition/execution issue.
Do not solve it by moving presentation before the trusted execution receipt.
