READ THIS FIRST
M4C3L fixes a concrete private-Room client defect and adds narrowly scoped authenticated browser media-element telemetry.

The exact post0016 Room client rebuilt every native-presentation audio element on changed Room snapshots.
A completed audio GET creates transport/journal provenance and changes the snapshot digest, so the next WebSocket snapshot could destroy/recreate the in-progress audio element.
M4C3L introduces stable keyed presentation/audio DOM reconciliation so unrelated snapshot updates do not replace the same presentation's audio element.

M4C3L also adds authenticated client media-element telemetry for playing and ended.
This telemetry is NOT:
- proof of audible speaker output;
- proof that a human heard/listened;
- peer-delivery confirmation;
- understanding confirmation;
- reply-causation evidence;
- speech-act execution;
- speech-act consequence-learning evidence;
- native choice/preference/relationship/cognitive-memory authority.

The browser/client layer remains distinct from:
NativePresentationRecord -> server NativeAudioTransportReceipt -> authenticated client media telemetry -> actual speaker output -> human hearing -> understanding -> later conversational outcome.

WHAT 0017 ADDS

1. STABLE KEYED NATIVE-PRESENTATION DOM
The Room no longer puts native-presentation audio elements in the generic view that is rebuilt on every snapshot.
Native presentation nodes are keyed by NativePresentationRecord.id.
The same presentation/artifact reuses the same HTMLAudioElement across unrelated snapshot updates.
This prevents a transport/journal/telemetry snapshot update from itself destroying the active media element.
No autoplay and no programmatic native-audio play() were introduced.

2. AUTHENTICATED CLIENT MEDIA-ELEMENT TELEMETRY
A dedicated typed NativeAudioClientPlaybackTelemetryReceipt persists only authenticated private-Room browser media-element telemetry.
Events are narrowly:
- playing
- ended

The play event is deliberately not used as the telemetry receipt event.

3. DURABLE PROVENANCE ORDER
playing requires:
- exact NativePresentationRecord;
- exact audio artifact;
- matching native text/audio hashes;
- genuine native voice presentation provenance;
- already-durable matching NativeAudioTransportReceipt;
- current private Room authentication;
- current Ed25519 owner-device session.

ended additionally requires:
- prior accepted playing;
- same presentation;
- same artifact;
- same owner device;
- exact same Room session-token SHA256;
- same client playback_session_id.

4. PERSISTENT IDEMPOTENCY
SQLite contains a dedicated audit/provenance table.
The persistent dedupe identity includes presentation, artifact, owner device, exact session hash, playback session and event.
Duplicate logical submissions reuse the existing receipt instead of creating duplicate semantic events/journal rows.

5. SECURITY / SESSION BINDING
Raw Room session tokens are never persisted by this telemetry.
The receipt stores only the SHA256 identity of the exact authenticated session.
Legacy bootstrap cannot submit this telemetry.
Nonprivate transport cannot submit it.
Cross-device or renewed-session ended cannot complete an older playback session.

6. ZERO COGNITIVE AUTHORITY
The typed receipt hard-fixes the following to false:
audible_output_confirmed
peer_delivery_confirmed
peer_heard_confirmed
peer_understanding_confirmed
peer_reply_causation_confirmed
semantic_truth_authority
answer_authority
speech_act_choice_authority
preference_label_authority
cognitive_memory_authority
relationship_authority
source_write_authority
deployment_authority

The client request schema does not contain fields that can submit hearing, understanding, preference, relationship or native-choice claims.

7. NO CONSEQUENCE LEARNING
Client playback telemetry does not:
- execute a speech act;
- clear pending speech-act execution state;
- update speech-act action observations;
- update speech-act transition observations;
- train expression/private-continuation policy;
- create cognitive memory.

Later conversational outcome remains separate.

8. SANITIZED PRIVATE ROOM SNAPSHOT
The Room snapshot may expose the owner device id and browser event identity for private audit.
It does not expose the private session SHA or device fingerprint.
Audible/hearing/understanding/native-choice/preference/relationship authority remains false.
