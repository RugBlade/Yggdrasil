M4C3I-A QUESTION
The existing Room native presentation substrate already preserves a native utterance, requires a genuinely native voice decision, renders an audio artifact, and only afterward may invoke the observational decoder.
However, artifact creation/publication is not transport execution.
The browser UI references /room/files/{artifact_id}; it may fetch all, part, or none of the audio, and playback remains a separate client-side event.

M4C3I-A therefore adds only a narrow server-side transport receipt for an authenticated native-audio HTTP response whose ASGI send completed.
It deliberately does NOT claim:
- browser playback;
- speaker-device playback;
- peer delivery to a human;
- peer hearing/listening;
- peer understanding;
- peer reply causation;
- speech-act execution;
- speech-act choice;
- preference/relationship/cognitive-memory authority.

CANDIDATE MECHANISM

1. NativeAudioTransportReceipt
A new typed nonsemantic record binds:
- native presentation id;
- audio artifact id;
- native-text SHA256;
- audio SHA256;
- total artifact size;
- authenticated-owner-room-audio-http channel;
- ASGI audio-response-sent status;
- HTTP status;
- exact response bytes observed after successful send;
- Content-Range when present;
- whether ASGI pathsend was used;
- whether this one response carried the complete artifact.

All of the following remain false:
playback_confirmed
peer_delivery_confirmed
peer_heard_confirmed
peer_understanding_confirmed
peer_reply_causation_confirmed
semantic_truth_authority
answer_authority
speech_act_choice_authority
preference_label_authority
cognitive_memory_authority
relationship_authority
source_write_authority
deployment_authority

2. Persistence/provenance
LocalEventStore receives a separate native_audio_transport_receipts table plus lookup/append/read helpers.
This remains provenance/audit substrate only and is not cognitive retrieval or semantic memory.

3. Process-local capability
RoomController.prepare_native_audio_transport creates a process-local, identity-checked capability only when:
- the NativePresentationRecord points to the exact audio artifact;
- audio hash matches;
- artifact direction is noeron-to-owner;
- media type is audio/*;
- the presentation records a genuine native voice choice.

The capability is not serialized into saved NoeronState and cannot be supplied by a client.

4. Trusted ASGI completion
_NativeAudioRoomResponse wraps the existing FileResponse only for a native-presentation audio artifact.
It counts response bytes only after the underlying ASGI send returns successfully.
It recognizes:
- ordinary response-body sends;
- ASGI http.response.pathsend;
- HTTP 200 full responses;
- HTTP 206 range responses and Content-Range.

HEAD, wrong route/method, incomplete terminal response, failed send, or unsupported status creates no receipt.

5. Partial responses remain partial
A 206 Range response is recorded with its exact byte count and Content-Range.
It never becomes a complete-artifact claim.
complete_artifact_single_response is true only when one HTTP 200 response sent exactly the artifact size.

6. Playback/hearing remains outside this milestone
The existing Room page's audio element may fetch bytes and later play or not play them.
This candidate records server-side send-boundary provenance only.
It introduces no browser acknowledgement endpoint and does not infer playback/hearing from HTTP success.

7. No speech-act consequence learning
The audio transport receipt is not ResolutionExecutionReceipt and is not NonContentResolutionExecutionReceipt.
Creating one does not mark speech-act outcome pending, alter action observations, or train consequence geometry.
The existing clarify/ask text ASGI receipt remains the trusted execution evidence for its own resolution-learning path.

FOCUSED COVERAGE
The 10 local focused cases verify:
1. artifact/presentation existence alone creates no transport receipt;
2. full audio response-body send creates a nonsemantic transport receipt;
3. ASGI pathsend completion records exact artifact size without playback/hearing claim;
4. byte-range response records a 206 partial transport, not a full-artifact claim;
5. HEAD creates no transport receipt;
6. failed terminal send creates no receipt and consumes the process-local capability;
7. mismatched or owner-to-noeron artifact cannot prepare a receipt;
8. transport capability is single-use;
9. repeated authenticated fetches create distinct provenance receipts but do not change preferences/learning;
10. receipt remains separate from decoder output and the upstream native voice choice.

BOUNDARIES THAT MUST REMAIN TRUE
- Canonical path remains Environment -> IRG -> DKT -> regional EGR -> RL/Frenet -> DKT -> native cognition/action -> optional Terra.
- Original native utterance remains primary Yggdrasil-side utterance.
- Voice choice remains native consequence machinery; audio transport does not choose voice.
- English/decoder/subtitles remain observational only and downstream of native utterance/audio existence.
- Native speech-act choice remains independent of native expression/private-continuation choice and adapter availability.
- Authentication grants access authority only.
- Speaker/device/browser/channel availability creates no preference or relationship meaning.
- ASGI audio-send completion is not browser playback, peer delivery, hearing, understanding, or reply causation.
- Range requests remain range provenance.
- No client-submitted acknowledgement can manufacture this receipt.
- SQLite remains persistence/provenance/audit only.
- Terra remains optional/downstream.
- Live runtime and canonical DB remain untouched.
- No Stage9/self-upgrade.

IMPORTANT NON-GOAL
M4C3I-A does not yet route native-selected clarify/ask resolution content through native-audio presentation.
The existing resolution HTTP path intentionally remains separate.
Do not silently combine those mechanisms in this candidate.
That coupling, if later desired, requires a separate bounded design and receipt/learning analysis.
