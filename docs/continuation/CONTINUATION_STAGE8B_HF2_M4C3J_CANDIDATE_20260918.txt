CANDIDATE MECHANISM

1. ResolutionExecutionReceipt stays primary
The existing trusted terminal POST /room/message JSON send remains the clarify/ask execution boundary.
No presentation object or audio fetch can replace that receipt.

2. Private exact native text stays process-local
_ResolutionRoomResponse receives the exact native utterance privately.
It is not added as an outward fallback, client acknowledgement or new authority surface.

3. Completion provenance returned by the trusted runtime
After durable complete_resolution_dispatch success, the in-process adapter receives zero-authority identity fields:
- receipt id;
- event id;
- action;
- channel;
- native-text SHA256.

This does not expose new semantic or native-choice authority.

4. Post-receipt presentation only
The adapter attempts native presentation only when:
- receipt_recorded=true;
- the exact private native text is still present;
- current Room embodiment configuration has a voice profile;
- sha256(private native text) matches the durable ResolutionExecutionReceipt native-text SHA.

No presentation is attempted before the trusted send/receipt boundary.

5. Independent native voice choice preserved
present_native_utterance still runs its existing native voice vs text-only consequence selection.
If no configuration/voice exists or voice choice resolves to text-only/unresolved:
- the already-valid clarify/ask execution remains valid;
- no audio presentation is created;
- no speech-act state is altered.

6. Explicit receipt-to-presentation provenance
NativePresentationRecord gains optional zero-authority fields:
source_resolution_receipt_id
source_resolution_event_id
source_resolution_action
source_resolution_execution_confirmed

For ordinary presentations they remain empty/false.
For resolution-derived presentations they can be populated only with a complete valid link whose native-text SHA matches the exact utterance.

7. Downstream failure isolation
If native voice rendering/presentation throws after the ResolutionExecutionReceipt is durable:
- the receipt remains valid;
- speech-act/expression pending state is not rolled back;
- no second execution is invented;
- the presentation error is logged as downstream failure.

8. Immediate response remains truthful
The response body cannot claim a post-send presentation already exists.
For a resolution dispatch:
presentation_id remains null
native_presentation_created remains false
native_presentation_deferred_until_execution_receipt=true

Authoritative later presentation state remains /room/state.

9. Audio transport remains separate
If a linked presentation later gets fetched:
NativeAudioTransportReceipt records only server-side audio HTTP send completion.
It does not mark a second speech-act outcome and does not train.

LOCAL FOCUSED CASES
1. successful resolution send creates presentation only after durable execution receipt;
2. terminal text-send failure creates neither receipt nor resolution presentation;
3. no native voice configuration leaves valid text execution and no presentation;
4. native voice text-only choice leaves valid execution and no audio;
5. downstream presentation failure cannot erase durable receipt;
6. private native-text hash mismatch blocks linked presentation;
7. incomplete/mismatched resolution presentation provenance fails closed;
8. ordinary presentation retains empty resolution-execution provenance;
9. resolution audio fetch remains transport-only and does not double-train;
10. completion return provenance is identity/audit only.
