CONCRETE DEFECT FOUND
Current exact post0017 Room JavaScript function postClientMediaEvent() retries HTTP 409 provenance races, but it does NOT retry a thrown fetch/network error.

Current structure:
- await fetch(...)
- parse JSON
- success returns
- HTTP 409 retries up to 10 times
- a thrown fetch/network error exits the function immediately.

The playing handler then catches the rejected promise and clears:
- dataset.playingReported
- dataset.playbackSessionId

The ended handler cannot submit the matching ended event once that playback_session_id has been cleared.

WHY THIS IS A REAL PROVENANCE DEFECT
A network failure is ambiguous about server commit state.
The server may have:
1. received and durably persisted the playing receipt; then
2. the response may have been lost before the browser observed success.

Because the server is already persistently idempotent, retrying the SAME request with the SAME playback_session_id is safe and is the correct way to resolve this uncertainty.
Without such retry, the durable server may contain playing while the client forgets the identity and later cannot attempt the linked ended record.

This does NOT create a false cognition/hearing claim, but it weakens the completeness and continuity of the telemetry provenance M4C3L introduced.
