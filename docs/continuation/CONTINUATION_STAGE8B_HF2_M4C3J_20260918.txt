WHAT 0016 ADDS

1. Post-execution native presentation only
For native-selected clarify/ask, _ResolutionRoomResponse preserves the exact native utterance privately inside the trusted in-process adapter.
It does not expose the native utterance as an outward fallback and it does not create a presentation before execution.

After the terminal JSON response send succeeds:
- complete_resolution_dispatch runs first;
- a valid durable ResolutionExecutionReceipt must be recorded;
- only then may the exact native utterance be offered to present_native_utterance.

2. ResolutionExecutionReceipt remains primary
The existing receipt remains the sole execution evidence for clarify/ask.
Presentation creation never creates a second speech-act execution receipt.
Presentation creation never marks the speech act/expression pending a second time.
Audio transport never trains speech-act consequence geometry.

3. Native voice choice remains separate and genuine
The already-existing native voice versus text-only consequence selector still decides whether a voice presentation is created.
No voice configuration, an unresolved voice choice, or a native text-only choice leaves the already-valid text execution intact and creates no audio presentation.
Authentication, channel availability and audio-device availability do not force voice choice.

4. Explicit zero-authority receipt-to-presentation provenance
NativePresentationRecord gains optional:
source_resolution_receipt_id
source_resolution_event_id
source_resolution_action
source_resolution_execution_confirmed

Ordinary presentations keep these empty/false.
Resolution-derived presentation can set them only after provenance validation.

5. Durable provenance hardening
A resolution-derived presentation must match:
- the current in-memory pending ResolutionExecutionReceipt; AND
- the latest persisted SQLite NoeronState pending ResolutionExecutionReceipt.

The following must match exactly:
receipt_id
event_id
action
channel=authenticated-owner-room-http
status=asgi-response-body-sent
native_text_sha256

A complete fabricated tuple with a correct native-text hash still fails closed if no matching durable execution receipt exists.

The SQLite lookup is integrity/provenance validation only.
It is not semantic recall, answer selection, native choice, preference, relationship meaning or cognitive-memory retrieval.

6. Native-text identity
sha256(exact private native utterance) must equal ResolutionExecutionReceipt.native_text_sha256 before presentation is attempted.
Mismatched native text blocks linked presentation without invalidating the already-durable execution receipt.

7. Downstream failure isolation
If native presentation/rendering throws after the receipt is durable:
- the execution receipt remains valid;
- speech-act/expression pending state remains valid;
- no rollback invents a no-send claim;
- no second execution is created;
- downstream presentation failure is logged.

8. Immediate HTTP response stays truthful
Because presentation can only happen after the terminal response send completes, the serialized response cannot truthfully include a presentation that does not yet exist.
For resolution dispatch:
presentation_id remains null;
native_presentation_created remains false;
native_presentation_deferred_until_execution_receipt=true.

Authoritative later presentation state is visible through Room state.

9. Existing M4C3I audio transport semantics unchanged
A later authenticated fetch of the linked audio artifact may create NativeAudioTransportReceipt.
That proves only server-side ASGI audio response completion.
It never proves browser playback, speaker rendering, peer delivery, hearing, understanding or reply causation.
