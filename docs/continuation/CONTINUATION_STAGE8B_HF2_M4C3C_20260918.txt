WHAT M4C3C IMPLEMENTS
1. A narrow authenticated-owner Room HTTP actuator for genuinely native-selected clarify/ask content.
2. Independent existing native express/continue-private selection remains required after act/content formation. A chosen clarification does not itself authorize expression.
3. A process-local, identity-checked, single-use dispatch object carries the prepared payload from ingest to the trusted ASGI response adapter. It never enters JSON, cookies, headers, audit state, saved model state, or a client receipt API.
4. Preparation/queueing/private observation creates no execution receipt, pending outcome, or consequence observation.
5. Only after await send(http.response.body) successfully returns for the terminal response body at POST /room/message, status 200, does the trusted adapter submit the actual emitted text digest to the runtime.
6. Completion rechecks the current event, turn, pre-knot digest, pre-residual, native act choice, native express choice, channel, emitted text digest, and absence of pending conflicts under the runtime lock.
7. A valid completion persists a typed nonsemantic ResolutionExecutionReceipt plus linked speech-act and expression pre-state. Receipt alone does not train either consequence model.
8. A later, distinct, nonempty conversational USER_MESSAGE created after completion is required before learning. Endogenous/nonconversational/same/pre-send-created/missing or mismatched receipt evidence remains unresolved. Existing native DKT security admissibility and nonworsening native residual checks still decide whether an observed transition is admitted.
9. Learning uses existing InitiativePolicy._mean and observe_resolution_transition; no new preference metric or canned policy was added. Once consumed, the pending outcome is cleared. The last receipt/audit remains provenance only.
10. A protected expression pending receipt cannot be overwritten by a later transport preparation. Persistence failure restores in-memory speech/expression state and the security checkpoint; consumed dispatch capability cannot be replayed.
11. Existing ordinary proof-supported answers retain their original response/transport path. Room owner commands and response-channel overrides cannot force this resolution actuator to claim native choice.
12. Existing Room authentication still requires the authenticated Ed25519 device session and permitted local/tunnel transport. Legacy bootstrap authentication is insufficient.

RECEIPT MEANING AND LIMITS
Receipt status: asgi-response-body-sent.
Channel: authenticated-owner-room-http.
Actions admitted: clarify, ask.
peer_delivery_confirmed=false.
This proves completion at the ASGI send boundary; it is not evidence that the peer received, displayed, read, understood, or answered the content. The existing ASGI send contract only requires flushing data into the send buffer before returning.
Primary source consulted: https://asgi.readthedocs.io/en/latest/specs/www.html#response-body-send-event
The adapter is a nonstreaming JSONResponse. Status/body are recorded only after the corresponding send returns. Failed send, wrong route/status/output, stale state, forged/replayed token, or conflict cannot establish a learnable receipt.
An event entering before send completion invalidates the prepared capability; a later completion may therefore drop learning evidence even if bytes were sent. It does not invent a no-send claim.
There is no client-submitted acknowledgement endpoint and no native-choice authority derived from authentication.
No native audio presentation is created for this narrow resolution HTTP actuator. Existing ordinary-answer presentation behavior is preserved.
